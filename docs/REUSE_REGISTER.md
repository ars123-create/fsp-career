## Как выполнять каждый следующий блок

1. Прочитать его критерий готовности и связанные R/O из требований.
2. Потратить 15–40 минут на адресный поиск; для каркаса максимум 60 минут, для алгоритма отдельный исследовательский бюджет. Сначала первичная документация и код.
3. Сравнить 1–3 кандидата по соответствию интерфейсу, лицензии, внешним сервисам, сложности запуска и адаптации. Не сортировать только по звёздам GitHub.
4. Зафиксировать URL + SHA/версию + дату + конкретные пробелы. Прочитать нужный исходник и лицензию.
5. В отдельном минимальном примере запустить компонент, затем проверить нашу адаптацию на входах из ТЗ. Зафиксировать команду и результат.
6. Интегрировать в модуль, пройти сквозную проверку, обновить реестр. Если не подошло — записать причину и взять более простое решение.

Шаблон записи реализации: **блок → требование → найденные кандидаты → выбранная версия → заимствованная часть → наша адаптация → команда проверки → результат → оставшиеся ограничения**. Требование сначала искать готовое закреплено также в [AGENTS.md](../AGENTS.md).

## Исключение, обоснованное для исследовательского прототипа

Для конечной модели в research/core.py были рассмотрены catsim, py-irt и научные аналоги. В изученных интерфейсах не найден готовый блок, который одновременно сохраняет общее скрытое знание семейства, перечисляет условные исходы проверки и оценивает изменение ограниченного назначения. Поэтому маленькая точная модель написана отдельно, а оптимизация назначения переиспользована из SciPy. Это не утверждение, что аналогичного кода нигде не существует. Математические свойства проверены независимо от хороших/плохих цифр benchmark; приложение ещё не использует эту модель.
