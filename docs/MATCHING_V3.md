# Подбор с уточнениями v3

7 октября 2026. Приложение **0.4.3-dev**, алгоритм вопросов `decision-evoi-v3`.
Работает на локальном стенде 8018; модель предпочтений осталась прежней.
[Ускорение вычислений и проверки 0.4.1](PERFORMANCE_0_4_1.md) описаны отдельно.
[Правило равных оценок и проверки 0.4.2](FSP_TIES_0_4_2.md) добавляют учёт
подтверждённого достижения после основной оценки навыков. Сохранённый архив
0.4.0-dev предшествует обоим изменениям; контейнер 8019 не заменён.
Независимая оценка людьми **NOT RUN**: пользователь сообщил,
что разработчика или рекрутера для такой проверки пока нет.

Дополнительный [аудит способов ввода](ELICITATION_AUDIT_0_4_2.md) проверил сам
адаптер на 1200 новых синтетических задачах: универсального преимущества
вопросов над прямыми весами нет; передача чисел и бинарные ответы дают разный
объём информации. Реальная точность и удобство ввода не измерены.

В 0.4.3 добавлен отдельный [прямой ввод приоритетов](DIRECT_WEIGHTS_0_4_3.md).
Кнопка в панели вопросов позволяет исправить предложенные доли. До применения
изменений ответы и результат сохраняются; применение переключает способ
ввода. Модель вопросов не перенастраивалась по результатам нового аудита.

## Что получает работодатель

В поиске выбрать Python backend → Middle → «Подбор с уточнениями» →
«Найти специалистов». Сервис сначала применяет обязательные условия,
затем выбирает до пяти профилей по наблюдаемым результатам проверок.
Когда содержательный вопрос может изменить подборку, показывает два условных
сочетания навыков: например, SQL 100% / API 50% против SQL 50% / API 100%.
Ответ уточняет относительную важность навыков. Это не оценка конкретного
человека и не вероятность его успешного найма.

Есть пропуск, скрытие вопроса, отмена последнего ответа и сброс. Максимум
три вопроса, возможна ранняя остановка. Можно сразу перейти к профилям.
Сохранённая подборка помнит ответы. После reload → «Мои подборки» возвращает
прежний состав, а «Обновить состав» пересчитывает его с теми же предпочтениями.
Публикация профиля и право видеть контакты проверяются заново.

## Расчёт и границы

Приоритеты трёх навыков представлены 3072 гипотезами: симметризованная
Sobol-квадратура равномерного распределения на симплексе. Исходно навыки
равнозначны. Ответ обновляет веса гипотез по мягкой логистической модели
с temperature=0.04 и lapse=0.02. Эти параметры — исследовательские допущения,
**не результат калибровки поведения работодателей**. Пропуск распределение
не меняет; противоречивые ответы не обнуляют все гипотезы.

Полезность профиля — сумма наблюдаемых процентов навыков с весами запроса.
Список максимизирует ожидаемую сумму полезности top-5. Следующий вопрос
максимизирует ожидаемый прирост этой суммы после ответа. Известный метод
EVOI адаптирован к конечному набору и сумме top-k; научная новизна не заявляется.
Условные свойства и независимые переборные проверки:
[PROOFS.md](../research/preference_topk/PROOFS.md).

Ожидаемый прирост не гарантирует пользу каждого фактического ответа.
В исследовании после 814 из 4800 вопросов реализованная потеря выросла.
Ранжирование основано на результатах короткого демонстрационного теста:
качество его измерений остаётся отдельным ограничением.

## Отличия приложения от замороженного исследования

Ядро `backend/app/preference_engine.py` скопировано побайтно; SHA указан в
`backend/preference_manifest.json`. Обёртка `preference_matching.py` отдельно:

- применяет публикацию, специализацию, грейд, зарплатную совместимость,
  формат и обязательные проверенные навыки до ранжирования;
- использует только исходные проценты навыков, без бонусов за свежесть,
  число семейств или ФСП; эти факты видны в профиле. При равной итоговой
  оценке подтверждённое неотозванное достижение с источником даёт приоритет;
  одного ФСП ID недостаточно. Отдельный ФСП-фильтр сохранён;
- ограничивает сценарий 100 подходящими профилями, 1–3 навыками и top-5;
  при превышении лимита просит уточнить фильтры, не отбрасывает профили тайно;
- убирает одинаковые, уже показанные и эквивалентные пары; спрашивает только
  о компромиссе, где у каждого варианта есть своя сильная сторона;
- прекращает вопросы при ожидаемом приросте не выше 0.05 условного балла
  на профиль; исследование использовало полный бюджет и общий пул пар;
- округляет расчёт для разрешения равных оценок до 12 знаков, затем
  использует наличие подтверждённого достижения и стабильный порядок ID;
  шум суммирования не меняет состав
  после пропуска. Отображаемый балл округляется до одного знака.

Поэтому результат исследовательского benchmark нельзя автоматически
приписывать интерфейсу приложения. Фильтрация пар и ранняя остановка
проверены функционально; отдельная оценка их качества людьми NOT RUN.

Ответы содержат только условные векторы баллов и выбор. В них нет ID, имён
или контактов кандидатов. Это предпочтения работодателя, не сертификаты
навыков; они не меняют грейд, зарплату или разрешения. API проверяет владельца
подборки, допустимые значения, число ответов, повторы и состав навыков.
Новая миграция не нужна: используется JSON `Need.ranking`, введённый в v2.

## Что показал заранее зафиксированный эксперимент

1600 синтетических задач, 8 сценариев, 5 стратегий, равный бюджет до трёх
вопросов. На основной группе 600 задач средняя модельная потеря: EVOI 0.4127,
BALD 0.5228 балла. Разница — **0.1101 балла**, или 21.1% относительно потери
BALD. Это не рост качества найма на 21%. EVOI проиграл BALD при резких
приоритетах и геометрической полезности, qEUBO — при полезности по слабейшему
навыку. Все результаты, проигрыш на development и ограничения сохранены:
[RESULTS.md](../research/preference_topk/RESULTS.md).

Протокол SHA-256:
`f5ef49b4656b56c4de7c2622ba6ae2e24cf18d1d9aa0f36eec878df6c62b38c0`.
После интеграции пять замороженных файлов v3 и пять файлов v2 повторно
сверены с протоколами. Ни данные, ни методы, ни метрики heldout не менялись.
