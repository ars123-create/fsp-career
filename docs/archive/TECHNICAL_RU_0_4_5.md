# ФСП / Карьера — техническая документация

Рабочая версия 0.4.5-dev, 8 октября 2026. Прежние комплекты, включая 0.4.4, сохраняются отдельно. Хакатонный MVP на демонстрационных данных. Источник требований — сохранённый PDF ТЗ ФСП, страницы 2–8; исходники и ограничения проверок перечислены в REQUIREMENTS.md и IMPLEMENTATION_STATUS.md.

## 1. Продукт и границы

Основной сценарий — обратный найм. Кандидат создаёт профиль и подтверждает навыки. Работодатель описывает потребность, видит обезличенную выдачу с подтверждениями и отправляет предложение с зарплатой в рублях. Контакты доступны именно этой компании после принятия приглашения. Независимый путь — самостоятельный отклик на вакансию этой компании. ФСП ID не обязателен.

Покрытие банка: Python backend и аналитика данных / SQL, Junior/Middle. Это ограниченная учебная рубрика. Калибровка сложности, эквивалентность форм на людях и устойчивость к внешнему ИИ ещё не доказаны. Система не должна автоматически принимать решения о реальном найме.

## 2. Архитектура

Браузер → React 19 / TypeScript / TanStack Router и Query → HTTP JSON / Bearer token → FastAPI → SQLModel / SQLAlchemy → PostgreSQL 16. Для локальной разработки допускается SQLite с WAL. Один модульный backend обслуживает API и собранный frontend. Схема версионируется Alembic. Docker Compose поднимает приложение, PostgreSQL и Mailpit, только на loopback.

Модули: auth.py — аккаунты и одноразовые действия; profiles.py и visibility.py — профили и единая граница видимости; assessments.py, assessment_bank.py и practical_bank.py — попытки, версионированное оценивание и грейд; matching.py и search.py — нормализация, фильтры и ранжирование; hiring.py — приглашения, вакансии и отклики; pdf_profile.py — экспорт; seed.py — только синтетическое демо.

13 таблиц: User, Candidate, Company, ActionToken, Attempt, Evidence, GradeAward, Need, Job, Invitation, Application, AuditEvent, LocalMail. User отделён от публичного профиля; Attempt хранит вариант, ответы, rubric и seed; Evidence хранит задания по семействам; GradeAward ссылается на конкретную попытку. Need хранит запрос и IDs исходной подборки, а не вечную копию персональных данных.

## 3. Аккаунты и приватность

Пароли хешируются Argon2 через pwdlib. JWT содержит purpose, audience, срок и версию сессии, проверяемую в БД. Logout, сброс пароля и смена email отзывают предыдущую версию. Одноразовые ссылки проверяют назначение, срок и consumed_at с условным UPDATE; в БД хранится только хеш токена. Лимитер попыток входа работает в памяти одного процесса, не является распределённой защитой.

Согласия на обработку и публикацию имеют отдельные даты и версию. Публикация требует обоих согласий. Отзыв публикации убирает профиль из новых поисков и восстановления старых подборок. Уже выданный контакт по принятому приглашению не исчезает от изменения публикации; кандидат отдельно отзывает доступ по приглашению. Отзыв отклика отзывает разрешение по этому отклику. Если у компании есть другое действующее основание, доступ остаётся.

Единая функция candidate_view формирует разрешённый ответ для API и PDF. До разрешения скрыты имя, email, телефон и мессенджер. Кандидаты не могут читать других кандидатов; работодатель не может использовать приглашение или подборку другой компании. Старый скачанный файл технически нельзя удалить с устройства получателя; отзыв действует на новые ответы и скачивания. API и PDF отдают no-store.

Контакты и URL в публичных текстах блокируются простой проверкой. Это защита от обычной случайной публикации, не надёжная анонимизация произвольного текста: сам кандидат может описать узнаваемый опыт. Не заявляется полная защита от реидентификации. Юридическое соответствие 152-ФЗ техническими тестами не установлено; публичная эксплуатация потребует политики, законного основания, места хранения, сроков удаления и процедур оператора.

## 4. Оценка компетенций

Профиль хранит заявленные специализацию/грейд отдельно от подтверждённых. Клиенту запрещено передавать подтверждённый грейд в редактировании профиля. Новая основная проверка — 12 заданий / 45 минут, из них 6 практических с двумя числовыми полями. Короткая — 3 практических / 12 минут раз в неделю по действующей категории. Старые попытки v1 сохраняют 6/3 заданий и прежние сроки. Эталоны создаются и проверяются на сервере, до завершения правильные ответы не входят в API. После завершения доступен разбор собственной попытки. История и ответы сохраняются; открытая попытка восстанавливается из интерфейса.

Вариативность: числовые параметры, массивы, таблицы и порядок заданий/вариантов. Проверки воспроизводятся по seed и rubric_version (2026-10-v1/v2/v3). До интеграции v2 сверены 4800 практических эталонов: 200 seeds × две специализации × два уровня × 6 заданий. SQL и фиксированный доверенный Python проверены выполнением, бизнес-сценарии — отдельными SQL-моделями, проценты — точными рациональными числами. Пользовательский код и выражения не исполняются. Старые property-проверки банка также сохранены. Числовые поля сохраняются явно; черновик не считается сохранённым. [Контракт, рубрика и доказательства v2](ASSESSMENT_V2.md).

Рубрики v2/v3: не менее 75% суммарно, 50% по каждому навыку и 50% практических заданий по каждому навыку. Оба поля практического задания должны быть верны. Для старых попыток применяется v1: 70% суммарно и 50% по навыку; результаты не пересчитываются. Подтверждённая категория изменяется отдельным GradeAward не чаще одного раза в 90 дней. Пройденная внутри интервала попытка сохраняется, применить её можно позже. До применения её навыки не заменяют подтверждения действующей категории. При применении сохраняется исходная дата проверки; ожидание не делает старый результат свежим. Неудачная попытка выше не понижает существующий грейд и не затирает его публичные подтверждения. Добровольная основная проверка ниже может изменить категорию после интервала. Спрос, зарплата, ФСП и алгоритм подбора грейд не меняют.

В 0.4.4 успешная основная форма задаёт набор семейств своей специализации, категории и рубрики. Короткая проверка обновляет только проверенное семейство, сохраняя остальные результаты. Среднее последних наблюдений по четырём семействам может измениться от одного ответа максимум на 25 процентных пунктов. Повтор не увеличивает покрытие. Сводная дата соответствует самому старому действующему наблюдению; один свежий ответ не обновляет все даты. Балл не является вероятностью владения навыком, а семейства не объявляются независимыми измерениями.

Старая рубрика и новая не смешиваются. Восстановление портфеля из истории допускается только при подходящей основной форме и однозначном порядке событий. Иначе короткая попытка остаётся в истории, прежний профиль сохраняется, интерфейс просит пройти основную проверку. Повтор завершения или получения уже выданного грейда не откатывает свежие результаты. Короткая проверка не меняет грейд. Работодательские авторские задания не реализованы: используется общий банк. Контракт и проверки — EVIDENCE_PORTFOLIO_0_4_4.md.

В 0.4.5 исправлено одно семейство Backend/Middle о повторе операции после сбоя. Прежняя форма принимала два неверных правила, поскольку каждый ключ в итоге завершался успешно. Новая содержит ключ только с откатом и ключ только с потерянным ответом после фиксации. На 200 заранее зафиксированных seeds для каждой версии оба ошибочных правила приняты в 200/200 старых и 0/200 новых вариантов. Правильные ответы совпали с независимым исполнением SQLite в 400/400 случаях. Это проверка программно заданных ошибок одного семейства, не калибровка квалификации людей. Старые задания и оценки сохраняются. Дополнительно получение старого отложенного грейда той же категории не заменяет более свежий портфель, в том числе другой рубрики. Подробности — ASSESSMENT_V3.md.

Защита от запоминания букв ответа и случайного распространения варианта ограничена небольшим числом семейств. Повторяемые шаблоны решаются по аналогии, а открытые исходники не позволяют обещать секретность банка. Внешний ИИ, прокторинг и сравнение независимых форм на людях — NOT RUN. До реального применения нужны расширение банка, экспертный аудит и пилот 8–15 добровольцев с двумя формами и независимой практической работой.

## 5. Подбор и объяснения

Нормализатор понимает небольшой словарь Python/SQL/API/аналитика/качество данных, специализацию, Junior/Middle, удалённый/гибридный/офисный формат и диапазон зарплаты. Распознанные поля видны и редактируются. Неизвестные обязательные навыки дают предупреждение; свободный текст не создаёт вымышленных подтверждений.

Жёсткие условия: опубликованный профиль с категорией; выбранные специализация/грейд/формат; пересекающиеся диапазоны зарплат при известных ожиданиях; по требуемым навыкам сохранённый балл не ниже 50%; достижения только при явном ФСП-фильтре. Отсутствие ФСП само по себе не мешает поиску. Поиск возвращает первые 100 профилей; большая база и пагинация требуют расширения.

Баллы = 0,80 × средний процент верных ответов + 10 × покрытие семейств + 5 × свежесть + 5 × достижения. Покрытие ограничено двумя семействами на навык; свежесть линейно убывает за 180 дней; вклад ФСП ограничен двумя подтверждениями. Это прозрачная исходная эвристика, не обученная вероятность найма. Объяснение строится из фактов: результат, дата, число семейств, пересечение условий, источник достижений. Зарплата — фильтр, не показатель квалификации.

Сохранённая подборка хранит нормализованные условия и первоначальные IDs. Можно открыть прежний состав и повторить запрос с текущими данными. Публикация и права перепроверяются, скрытые профили не восстанавливаются из старого снимка.

Дополнительные режимы: [устойчивый top-5 v2](MATCHING_V2.md) и [подбор с уточняющими сравнениями v3](MATCHING_V3.md). Режим v1 остаётся исходным. Уточнения сохраняются с потребностью работодателя; грейд и контакты не меняются. Их отдельные протоколы и отрицательные результаты не подменяют независимую оценку найма.

В v3 работодатель сравнивает два условных сочетания результатов проверок при одинаковых остальных условиях. Начальное распределение весов трёх навыков симметрично. Байесовское обновление после ответа изменяет предпочтения этой потребности. EVOI выбирает следующий вопрос по ожидаемому улучшению полезности всей пятёрки, а не по одной только неопределённости весов. Это применение известного принципа ценности информации; научная новизна не заявляется. В интерфейсе можно дать до трёх ответов, пропустить вопрос, отменить ответ или сразу перейти к результатам. Пропуск исключает предложенную пару, но не меняет предпочтения. При изменении подтверждений и публикации кандидатов подборка пересчитывается с актуальными правами.

Исследовательское ядро v3 сравнивалось с random, uncertainty, BALD и qEUBO при одинаковом бюджете трёх вопросов и одинаковом обновлении предпочтений. В основной заранее заданной группе из 600 синтетических задач (три сценария × 200 seeds, 18 профилей, три навыка, top-5) средняя потеря полезности относительно всезнающего выбора составила 0,4127 у EVOI и 0,5228 у BALD на условной шкале 0–100. Абсолютная разница −0,1101, относительное снижение 21,1%; описательный bootstrap-интервал разницы: [−0,1746; −0,0431]. Это свойства модели и протокола, не показатели качества найма людей.

Весь heldout содержит 1600 задач в восьми сценариях. EVOI уступает BALD при полярных предпочтениях и геометрической полезности; в сценарии слабого звена qEUBO лучше EVOI. В 814 из 4800 отдельных вопросов EVOI наблюдаемая потеря выросла. На dev EVOI в среднем проиграл BALD на 10,1%; исходный результат сохранён. Набор и веса не подстраивались по heldout. В приложении отдельно ограничены условные пары и добавлена остановка по ожидаемой пользе: цифры исходного протокола нельзя автоматически приписывать адаптеру. Замороженный код, seeds и сырые результаты: research/preference_topk/. Калибровка модели ответов и независимая оценка подборок людьми — NOT RUN.

В 0.4.3 добавлен прямой ввод приоритетов: от одного до трёх навыков с неотрицательными конечными весами и положительной суммой. Пропорции нормируются; интерфейс объясняет шкалу через пользу роста результата с 50% до 100%. Можно отредактировать предложенные после ответов доли, сохранить запрос и вернуться к новому диалогу. Нулевой вес не снимает обязательный фильтр. Контракт и проверки — DIRECT_WEIGHTS_0_4_3.md.

Этому решению предшествовал отдельный зафиксированный аудит 1200 синтетических задач: шесть сценариев, 24 профиля, три навыка, top-5, восемь способов ввода. В пяти из шести сценариев описательный интервал разницы EVOI с тремя фиксированными вопросами включает ноль: преимущество не установлено, эквивалентность не доказана. Точный прямой ввод часто лучше в линейной модели, но передаёт больше информации, чем три бинарных ответа. Ошибки числового ввода заданы искусственно; удобство и точность людей не измерены. При шумных подтверждениях 76 из 200 случаев EVOI хуже равных весов. Все исходные случаи и отрицательные результаты сохранены в research/elicitation_controls/; это не новый неизвестный набор для дальнейшей настройки.

В 0.4.2 подтверждённое действующее достижение ФСП разрешает равенство основной оценки в режиме уточнений. Введённый ID сам по себе преимущества не даёт. Ускорение 0.4.1 сохраняет прежнюю математическую модель; оно не доказывает улучшения качества подбора. Грейд и контактные разрешения остаются отдельными механизмами.

## 6. Приглашения и вакансии

Предложение не требует Job. Нужны заполненная компания, роль, описание, contact и salary_min/salary_max > 0, максимум не меньше минимума, валюта только RUB. Срок — 14 дней. Статусы sent/viewed/accepted/declined/withdrawn/expired. Повтор одинакового действия идемпотентен; конфликт accept/decline разрешается условным UPDATE. Частичный уникальный индекс запрещает два активных приглашения одной пары. PostgreSQL row locks сериализуют важные изменения.

Вакансии имеют того же владельца-компанию и обязательную зарплатную вилку. Кандидат может откликнуться без ФСП и подтверждённого грейда; это добровольный путь. Отклик уникален на пару кандидат/вакансия, контакты открываются только её работодателю. Сам факт публикации компанией не означает проверки её добросовестности.

## 7. Интеграции и расширение

ФСП: ввод ID создаёт pending-заявку и не выдаёт достижение. Демо-достижения записывает seed из явно синтетического источника. Реальный контракт предполагает проверку владения ID, issuer/source_event_id, event_date, результат, навыки, статус отзыва и время синхронизации; до получения официального API этот адаптер не подключён. Нельзя считать введённый ID доказательством личности.

Keycloak: будущий OIDC identity adapter с проверкой issuer/audience/nonce и связью issuer+sub с локальным User; не сопоставлять аккаунты по одному неподтверждённому email. ATS: будущие webhook-события с outbox, идемпотентностью и минимальным набором данных, экспорт контактов только при действующем разрешении. Эти интеграции описаны, но не реализованы.

Компании: следующий этап — подтверждение домена/реквизитов, модерация предложений, жалобы и ограничения подозрительной активности. До этого интерфейс не называет компанию проверенной.

## 8. Проверки и фактические результаты

В версии 0.4.5 по 181 backend-тесту PASS на SQLite, PostgreSQL и в изолированном Docker. В том числе проверены исправленное транзакционное задание v3, сохранение более свежего портфеля при получении отложенного грейда, сохранение семейств, повторы, старые рубрики, прямые приоритеты, равенства и отзыв достижения, новый числовой контракт, границы практической рубрики, сохранение v1 и 4800 практических эталонов. Проверены роли/IDOR, API/PDF контактов для двух работодателей, отзыв, одноразовость и просрочка ссылок, смена email и пароль, конфликт приглашений, дубликаты, salary validation, старые подборки, публикация, самостоятельный отклик, история и интервал грейда, банк/эталоны. Frontend собирается TypeScript/Vite; предупреждение о крупном JS chunk сохраняется. Миграция и alembic check проходят на обеих БД, включая заполненные базы. OpenAPI содержит входы, ответы и ошибки 45 операций.

Полный браузерный путь 0.4.5 пройден на отдельном локальном стенде: новый кандидат без ФСП, основная проверка v3 из 12 заданий, восстановление сохранённого ответа, новый работодатель без вакансий, уточнение и сохранение подборки, приглашение с вилкой RUB и принятие. Имя и email открылись работодателю этого приглашения, у второго нового работодателя остались скрыты. ## 9. Эксплуатация и ограничения

README описывает Docker и локальный запуск. Миграции применяются перед стартом. .env исключён из Git/архива, случайные значения генерирует scripts/setup.py. Локальные порты не публикуются во внешнюю сеть. Продуктовый публичный запуск ещё не выполнен: нужны хостинг, HTTPS, SMTP и политика хранения. Демонстрационные входы следует отключить, демо-данные отделить от настоящих.

PDF импорт ограничен 5 MB, 15 страницами и размером распакованного содержимого; изображения требуют OCR, которого нет. Проверка распакованного потока происходит после декомпрессии, поэтому для недоверенных больших файлов нужен отдельный ограниченный процесс. Необработанные PDF не сохраняются. SQLite подходит для локального стенда; для конкурентной записи целевым является PostgreSQL. Полный аудит безопасности, резервное восстановление, длительная нагрузка и защита нескольких процессов не выполнены.

## 10. Происхождение компонентов

От Full Stack FastAPI Template (MIT, commit e99fbaeba3b55190156ebae525ad9d481d76677e) адаптированы небольшие части security и UI-примитивы shadcn. Весь upstream как приложение не запускался; минимальные выбранные компоненты проверены отдельно. Radix/shadcn — готовые элементы, композиция интерфейса — по заранее сгенерированному ориентиру. Manrope — локально, OFL; PDF — ReportLab BSD, импорт — pypdf BSD; SQLModel/FastAPI/SQLAlchemy/Alembic — лицензии сохранены. Реестр содержит дату, ссылки, версии, пробелы и статусы. Зависимости закреплены lock-файлами. Код не заявляется научно новым только из-за сочетания библиотек.
