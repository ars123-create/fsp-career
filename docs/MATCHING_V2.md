# Устойчивый подбор v2: что сделано и что доказано

7 октября 2026. Рабочая версия приложения 0.2.0-dev. Архив сдачи 0.1.0,
его презентация и видео сохранены без изменений и **не содержат эту функцию**.

## Смысл для работодателя

Обычный рейтинг предполагает равную важность выбранных навыков. Новый отдельный
режим «Устойчивая пятёрка» рассматривает разные допустимые приоритеты, выбирает
до пяти профилей и показывает худший проигрыш лучшей возможной пятёрке.
При этом средняя исходная оценка может снизиться максимум на 1 пункт из 100.
Если уточнение важности двух навыков помогает уменьшить неопределённость,
сервис предлагает вопрос. «Пока не знаю» ничего не меняет. Сохранённый запрос
помнит ответы; публикация профиля и разрешения на контакты проверяются заново.

Для демонстрации: открыть локальный поиск, выбрать Python backend, Middle,
включить «Устойчивая пятёрка», нажать «Найти специалистов». В существующей
вымышленной базе 8 подходящих профилей. В ручной проверке до уточнения граница
была около 7.8 пункта на профиль, после ответа «SQL важнее API» — около 0.2.
Это изменение области допустимых предпочтений, **не измеренное улучшение
качества людей или реального найма**. Набор профилей для красивой цифры не меняли.

## Математическая гарантия

Фиксируем признаки, область приоритетов W, линейную полезность, k и baseline B.
Ищем S с минимальным worst-case regret при ограничении номинальной потери ε.
При точном решении S имеет не больший худший regret, чем B, и теряет не больше
ε номинальной суммы. Уточняющий правдивый ответ сужает W; при неизменных данных
и одном baseline оптимальная худшая граница не возрастает. Сам regret выбранного
набора вычисляется независимо от solver и имеет конкретный худший сценарий.

Полные выводы: [PROOFS.md](../research/robust_topk/PROOFS.md). Это обычное
математическое доказательство для явно заданной модели, не формальная
верификация Lean/Coq. Численная реализация имеет допуски и ограничение времени;
при недоказанном optimum показывается bounded/fallback и остаточный gap.
Границы в интерфейсе округляются вверх.

Общие методы minimax regret, MILP, elicitation и защита номинального качества
известны: [Viappiani–Boutilier 2009](https://www.cs.toronto.edu/~cebly/Papers/Viappiani_Boutilier_recsys09.pdf),
[Kasperski–Kurpisz–Zieliński](https://cs.pwr.edu.pl/zielinski/publications/papers/ipl12.pdf),
[Fischetti–Monaci, Light Robustness](https://www.dei.unipd.it/~fisch/papers/slides/2007%20AIRO%20%5BFischetti-%20Light%20Robustness%5D.pdf).
Собственная инженерная работа — совместная модель приоритетов/подтверждений,
компактная формулировка, пересчёт свидетеля, согласованный baseline в ветках,
адаптер к профилям и готовый пользовательский сценарий. Научная новизна не доказана.

## Что показал эксперимент

500 новых синтетических задач, 18 профилей в каждой, k=5, 7 методов; код и
протокол зафиксированы хешами до запуска. Старые research/test_v1 и
validation/matching-v1 не изменялись. Все числа и отрицательные результаты:
[RESULTS.md](../research/robust_topk/RESULTS.md),
[исходный JSON](../research/robust_topk/results/heldout_v2.json).

| Сценарий внутри модели | Снижение среднего худшего regret против mean | Изменение средней реализованной потери |
|---|---:|---:|
| Точные наблюдения | 18.8% | 0.0655 → 0.1002, хуже |
| Заданные интервалы | 12.6% | 0.1145 → 0.1407, хуже |
| Резкие приоритеты | 12.2% | 0.2252 → 0.2367, хуже по точечной оценке |

Это разные цели. Оптимизация worst-case автоматически не улучшает average-case.
Сравнивать вариант с вопросом с baseline без вопроса недостаточно: информации
получено разное количество. Дополнительный post-hoc анализ с одинаковым ответом
показал, что updated mean в среднем лучше robust во всех трёх in-model сценариях.
Он помечен разведочным и не выдан за заранее запланированную проверку. Поэтому
новый метод — дополнительный инструмент оценки устойчивости; обычный поиск
по умолчанию сохранён. Выбор «победного алгоритма» по реальной релевантности
по-прежнему требует независимой разметки.

## Граница исследования и приложения

- Research допускает заданные интервалы признаков и проверяет их алгебру.
  Приложение использует **точки наблюдаемых баллов**, не выдуманные confidence
  intervals способности человека. В нём неопределённы только приоритеты.
- Вектор каждого навыка: 80% наблюдаемого результата, 10% числа семейств с cap 2,
  5% свежести с горизонтом 180 дней, 5% подтверждённых достижений с cap 2. Это
  прежние инженерные веса evidence-v1, не обученная оценка пригодности.
- До оптимизации действуют публикация, категория, зарплатная совместимость,
  формат, обязательные проверенные навыки и явно включённый фильтр ФСП.
- Нет ФСП — искать работу можно. Грейд, зарплаты и контакты solver не меняет.
- До 100 подходящих кандидатов, 1–3 навыка, k≤5. Больше — явная просьба уточнить
  фильтры; скрытого обрезания базы до оптимизации нет. 0.6 с на основной solve,
  0.25 с на ветку вопроса; это лимит решателя, не строгий wall-clock SLA API.
- Новая БД-колонка need.ranking хранит режим/приоритеты; миграция 20261007_02.
  Перед обновлением локальной SQLite сделана резервная копия внутри data/backups.

## Воспроизведение

```sh
python3 -m venv .venv-matching
.venv-matching/bin/pip install -r research/robust_topk/requirements.txt
.venv-matching/bin/python -m research.robust_topk.smoke_scipy
.venv-matching/bin/python -m pytest research/robust_topk/test_core.py -q
# Новый файл, исходный результат не перезаписывается:
.venv-matching/bin/python -m research.robust_topk.benchmark --split heldout --output /tmp/fsp-heldout-reproduction.json
# Приложение и миграция:
sh scripts/start.sh
```

Для графика дополнительно нужен matplotlib==3.10.8, затем
`python -m research.robust_topk.report`. Алгоритм приложения — точная копия
замороженного core.py; тест сравнивает байты. Обёртка отдельно проверяет
численный gap перед меткой optimal. Внешнего LLM/API и обучения нет.
