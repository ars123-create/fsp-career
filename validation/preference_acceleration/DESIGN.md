# Ускорение вычисления того же EVOI

7 октября 2026. Начато после capacity-100-varied-baseline.json: 30 клиентов,
p95 2329.52 мс, 180/180 HTTP200, ноль семантических нарушений. Основной
ограничитель ещё не профилирован; ускорение проверяется до интеграции.

Готовый компонент: NumPy 2.4.4 `linalg.multi_dot`, BSD-3-Clause, уже в проекте.
Прочитаны документация и локальный `_multi_dot_three`; воспроизведён отдельно
пример с тремя матрицами. Он выбирает порядок умножения по размерам, сохраняя
само матричное произведение. Новый движок, кэш персональных данных, изменение
порогов, параметров ответа и отбор меньшего числа вопросов не вводятся.

Для линейной полезности U = W Xᵀ, где W — гипотезы весов, X — навыки профилей.
Для блока вопросов A = likelihood × posterior. Вклад первой ветви A U можно
считать как (A W) Xᵀ. Вместо дорогого произведения по всем профилям сначала
получаем три взвешенных признака. NumPy выбирает порядок автоматически.
Вторая ветвь, сумма top-k, весь допустимый пул и шум ответа сохраняются.
Приложению нужен только EVOI; вычисления BALD/энтропии/qEUBO остаются в
исследовательском ядре, но в быстром пути для приложения не выполняются.

Изменение порядка операций может изменить округление. В области до 100
профилей / 3 навыков / 3072 гипотез применяется запас 1e-10 для близких
максимумов и порога остановки. В этих случаях вызывается исходный полный
расчёт, чтобы сохранить его выбор при ничьей и на границе. Это консервативная
численная защита, не сертификат ошибки для произвольных матриц.

До интеграции: независимый перебор маленькой задачи; сравнение всех gains и
выбранных вопросов с замороженным ядром; posterior после ответов/пропусков;
ничьи и порог; отсутствие изменений входов; недопустимые формы. Затем те же
API-нагрузки с сохранением исходного провала и полной стоимости запроса.
Исследовательский heldout не используется для настройки; ускорение не
устанавливает новое преимущество качества рекомендаций.

Первая изолированная адаптация: 28 тестов PASS. Парный замер показал ускорение
100 разных профилей 183.32 → 74.56 мс, но сетка рубрики стала медленнее
5.31 → 8.43 мс из-за повторного расчёта при ничьей. Результаты и код v1
сохранены (`preference-acceleration-component.json`, `archive/prototype_v1.py`).
Во второй адаптации пул до одного блока (128 пар) сразу использует исходный
расчёт. Это устранение двойной работы; качество/пул/порог не меняются.

Повторный компонентный замер v2: разнообразные 100 профилей 182.26 → 71.56 мс;
сетка рубрики 5.36 → 7.09 мс. Поэтому при интеграции адаптер приложения для
пула ≤128 пар вообще не вызывает helper и сразу выполняет старую ветвь.
Результаты обоих прототипов сохранены. 28 проверок прототипа PASS до интеграции;
в приложении добавлены те же 28 проверок и 4 сравнения адаптера с reference.

Итоговый API-замер на тех же данных/протоколе/нагрузочном скрипте:
разнообразные профили, 30 клиентов, p95 2329.52 → 1679.98 мс;
сетка рубрики 1326.85 → 1272.17 мс. По 246 HTTP 200 на набор, нарушений нет.
Это performance-development; исходный FAIL сохранён. По 94 теста приложения
PASS на SQLite, PostgreSQL и Linux/Docker. Подробности и ограничения:
[PERFORMANCE_0_4_1.md](../../docs/PERFORMANCE_0_4_1.md).
